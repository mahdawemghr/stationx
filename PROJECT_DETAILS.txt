1. WHAT IT IS
-------------
StationX is a strength + cardio training log for phones, built with Flutter (Dart). You follow a fixed
ROTATION of workouts (for example Chest + Biceps -> Back + Triceps -> Legs + Shoulders), log every set,
rep and weight, and the app calculates volume, estimated one-rep max (1RM), progression suggestions
("add a rep", "go up 2.5 kg"), personal records (PRs) and muscle coverage for you. Cardio (runs, treadmill,
bike, rowing, swimming, sports and 33 activity types in total) is logged as well, live or after the fact.

IMPORTANT — the app is ONLINE-FIRST (it used to be local-first; that was replaced on 2026-10-10/14):
  * Every user has a USERNAME + PASSWORD account (no e-mail). All training data lives in a private
    account on Supabase (PostgreSQL). Supabase is the ONLY source of truth for user data.
  * You must be online to log in, load your data and save changes. A change is shown as saved only after
    the server confirmed it. If the network fails, the screen says so, keeps what you typed and offers Retry.
  * There is no guest mode, no offline mode, no local database of workouts and no background sync engine.
  * The only things kept on the phone are temporary/device-level state: the workout you are recording right
    now (a draft that survives the app being killed), the Health Connect opt-in and the Health Connect work queue.
  * Optional, off by default: Health Connect (Android) / Apple Health (iOS) integration (saving workouts there,
    importing workouts from a watch, heart-rate info). Sleep / resting heart rate / the "recovery" summary were REMOVED.
  * PROGRAM RULES (2026-10-11): the training program is generated ONCE (onboarding) or when the user explicitly asks
    to regenerate (with a confirmation). It never changes on login, restart, refresh, workout completion or rotation
    advance. New accounts start with NO routines. Generation, the weekly goal (training days + rest days = 7) and the
    rotation pointer are three separate things. The strength logger has no rest timer, no elapsed timer and no
    automatic ending by duration; new strength sessions store no duration (old ones keep theirs).

3. THE BIG PICTURE (ONLINE-FIRST)
---------------------------------
   Widgets ── read ──▶ Repositories (synchronous getters over an in-memory READ MODEL of the signed-in user)
      │                       ▲  filled by OnlineStore.load() after login / on app resume (paged, parallel)
      └─ write ─▶ Repository.write() ─▶ RemoteGateway (PostgREST upsert/delete or an sx_* RPC; 20 s timeout)
                       │  one serial "write lane" per store (writes never interleave)
                       └─ ONLY after the server confirmed: update the read model + notify listeners

Why this shape: the whole domain layer (PRs, progression, calendar, recommender, coverage) is pure Dart that
works synchronously over the full history. Keeping synchronous repository interfaces over an in-memory cache
meant ~40 screens did not need to be rewritten as async queries. The read model is NEVER persisted: it is
rebuilt from Supabase on login and cleared on logout.

Key guarantees
  * Server-first writes: a repository write throws a typed RemoteException on failure and leaves the read model
    untouched. UI shows an error + Retry and keeps the user's input. No fake success.
  * Atomic multi-row changes: saving workouts together with the rotation, finishing a workout together with the
    rotation move, first-time account set-up and "delete all my data" are single Postgres functions (RPC).
  * Epoch guard: a counter bumped on login/logout/account change. A load or write that started under an older
    epoch never touches the read model afterwards, so a late response for user A can never appear for user B.
  * Snapshot guard: if a save started or finished while a refresh snapshot was in flight, the snapshot is
    discarded (it might predate the save and undo a confirmed change); the next refresh catches up.
  * Idempotent writes: ids are generated on the client, so a retry after a lost response cannot duplicate data
    (upsert on (user_id, id); sx_finish_workout is idempotent on the session id).
  * Hard deletes: deleting removes the row on the server immediately. No tombstones, no soft-delete columns.
  * No realtime subscriptions: single-user private data; data is re-read when the app returns to the foreground
    (throttled to once per 30 s) or on "Retry".


4. PRODUCT RULES (do not break)
-------------------------------
  P1  ROTATION IS A SEQUENCE, NOT A CALENDAR. The next workout is the next one in the program; if you skip a day
      you just continue. The rotation advances ONLY when a workout is completed. Backdated entries never move it.
        - Completing the CURRENT workout -> index + 1 (wraps).
        - Completing a different workout that is in the rotation -> pointer moves to the position AFTER it
          (first occurrence at/after the pointer).
        - Completing a workout that is NOT in the rotation (archived / ad hoc) -> rotation unchanged.
  P2  workoutDate (when you trained; editable / backdatable) is ALWAYS separate from createdAt (when the row was
      entered). Windows, calendars, charts and PRs use workoutDate.
  P3  All calculations (e1RM, volume, PRs, progression, coverage, recommendations) live in the pure-Dart domain
      layer. UI widgets never calculate them.
  P4  Server confirms before the UI says "saved". Every write call site uses runRemote() (single-flight per key,
      success message only after confirmation, error snackbar with Retry that says plainly nothing was saved).
  P5  Cardio input fields adapt to the activity type (distance, pace, speed, incline, resistance, calories...).
  P6  Honest data: no fake numbers. Stitch mock-only features (GPS, sensors, mesocycles, social) were replaced with
      honest "not available" states. Health data written/read only contains what the user logged or confirmed.
  P7  Exercise weights are stored in kg everywhere; kg/lb is a display setting. Distances are stored in km.
  P8  Screens use theme tokens (context.sx, SxText, SxSpace); no raw colours.
  P9  Saving a new schedule ARCHIVES previous workouts (they stay openable/startable/editable and can be added
      back); they are deleted only if the user deletes them.
  P10 Seed/built-in exercises ship in the app; only CUSTOM exercises are user data.

6. APP LIFECYCLE & ACCOUNTS
---------------------------
6.1 Start-up (bootstrap.dart)
  1. Global error handling: in release builds ErrorWidget becomes a friendly message and exceptions are logged by
     TYPE only (no data).
  2. SupabaseConfig.validate(url, key). Missing/invalid config -> StartupErrorApp.notConfigured ("StationX is not
     configured") and nothing else runs. The config guard REFUSES: non-https URLs, "sbp_" access tokens,
     "sb_secret_" keys and JWTs whose payload contains "service_role".
  3. Open the Isar device store (documents directory, db name "stationx"). On failure -> StartupErrorApp with
     "Try again" and "Reset device storage" (deletes only the draft + preferences file; never user data).
  4. Supabase.initialize(url, publishableKey). On failure -> "Couldn't start" with Try again.
  5. Health Connect (Android/iOS) or no-op repository; HealthSyncService with a JSON file store next to the DB.
  6. OnlineStore(SupabaseRemote(client), device) + AppController(... auth: SupabaseCloudAuth(client)).
  7. runApp(StationXApp) then controller.init() restores the saved Supabase session and loads the data.
  The system navigation-bar colour follows the theme (Obsidian / OLED).

6.2 SessionPhase (the root widget switches on it)
  restoring  -> looking for a saved session at start-up          (SessionSplash)
  signedOut  -> nobody signed in / session ended                 (LandingPage)
  loading    -> signed in, loading the user's data               (SessionSplash)
  ready      -> data loaded, app usable                          (MainShell: 4 tabs)
  loadFailed -> signed in but loading failed (offline/server)    (LoadFailedScreen: Try again / Log out)
  Rules: every boot carries a generation number (stale boots are discarded); boot is single-flight per user;
  an auth-expired error anywhere (read, write, RPC) ends the session; a session ending from ANYWHERE pops every
  pushed screen and shows the landing page so nothing of the previous user stays visible; the landing page can
  show "Your session expired. Please log in again."
  Resume: when the app returns to the foreground the Health status is refreshed and the server data is re-read
  (throttled 30 s, skipped while a save is in flight). A failed background refresh only shows a small
  "may be out of date — tap to retry" banner above the bottom navigation; it never replaces the screen.

6.3 Accounts (USERNAME + PASSWORD only — no e-mail, ever)
  * Username: trimmed + lower-cased everywhere; validated by Username.validate (allowed chars A-Z a-z 0-9 _ . -,
    must start/end alphanumeric, length limits, reserved names such as the app/staff/system names are rejected).
  * Supabase Auth needs an e-mail-shaped identifier, so the username is mapped to a PRIVATE, non-routable
    "<username>@stationx.local" (never shown; Username.fromIdentifier maps it back). No mail is ever sent.
  * Password policy shown while creating an account: >= 8 characters, one uppercase letter, one digit (the server
    itself enforces only min length 8). Password goes straight to Supabase Auth; never stored or logged.
  * Server auth settings (verified 2026-10-10): e-mail auto-confirm ON (sign-up returns a session immediately),
    min password 8, Site URL = dev.mahdi-haji.stationx://auth-callback.
  * NO password reset by design (no e-mail on file). The Create-account screen and the privacy policy say so.
  * Register: AccountForm -> signUp -> boot (loads data; the server creates the profile via the signup trigger and
    the client calls sx_init_account with NO routines, exactly once, so the new account is empty) -> About you -> Schedule setup
    (split -> equipment -> [days] -> training/rest days -> review -> save).
    If signing up worked but the data could not be loaded, the session is ended again so the form can simply be
    re-submitted. Login: signIn -> boot -> enter the app.
  * Friendly auth errors (CloudAuthStatus): invalid credentials, user exists, weak password, rate limited, network,
    unavailable, sign-up incomplete, unknown (strings in features/cloud/cloud_strings.dart).
  * Log out: confirm dialog (warns only about an unfinished workout, which lives on the phone and is discarded);
    clears the read model, the draft and the notice, drops the Supabase session, shows the landing page.
  * Delete account: Profile > Delete account -> RPC delete_account() (security definer; deletes only auth.uid(),
    cascades to every table) then local sign-out.
  * "Delete all my data": RPC sx_reset_account_data() wipes every training row but keeps the login and profile
    settings; the account is re-initialised, still without any routine.
  * Public deletion page for Google Play: docs/web/delete-account.html (to be hosted).


7. DATA FLOW: READS & WRITES
----------------------------
7.1 Reads
  OnlineStore.load(userId, username) fetches in parallel: profile, rotation, exercises (custom), workouts,
  workout_sessions, cardio_sessions, cardio_goals, custom_cardio_activities. List tables are paged with a
  keyset cursor (order column + id, 500 rows/page; sessions newest-first by workout_date). Rows the client cannot
  parse are skipped and counted (one bad row never makes an account unloadable). If the profile has no
  initialized_at, the client calls sx_init_account (no routines) to mark it initialised, then reads again.
  _apply() then fills the repositories: exercises = built-in catalogue (420) + the user's custom ones (a custom
  row with the same id as a built-in replaces it); workouts sorted by `position`; sessions; cardio + goals +
  custom activities; profile (username shown from the stored identifier).

7.2 Writes (online_repositories.dart)
  Every write goes through OnlineContext.write(): serialized in one lane, server call first, read model second,
  skipped silently if the epoch changed meanwhile. Mapping:
    ExerciseRepository.addCustom ...... upsert exercises
    WorkoutRepository.saveWorkout ..... RPC sx_save_workouts(workouts, delete_ids, rotation)  (plan computed when
                                         the write's turn comes, so it starts from the latest read model)
    .deleteWorkout / .saveSchedule /
    .replaceAll ....................... RPC sx_save_workouts (atomic: routines + rotation together)
    .setRotation / setCurrentWorkout .. upsert rotations
    Finish workout .................... RPC sx_finish_workout(session, rotation|null)  (AtomicWorkoutFinisher)
    SessionRepository.add/update/delete  upsert / delete workout_sessions;  addAll = one upsert call per <=100 rows
                                         (a huge import is therefore several requests; NOT atomic across batches,
                                         but idempotent, so re-running it completes the rest)
    CardioRepository ................... upsert/delete cardio_sessions, cardio_goals, custom_cardio_activities
                                         (saveGoals saves several goals in one request)
    ProfileRepository.update .......... upsert profiles
    resetData ......................... RPC sx_reset_account_data, then re-init + re-read

7.3 Errors (RemoteException, remote_exception.dart)
  Every failed Supabase call becomes one of:
    offline      no connection / timeout / DNS — nothing saved, retry is safe
    authExpired  session gone/expired/revoked — user must log in again (handled globally)
    rejected     server refused the data (constraint/policy/validation: PostgreSQL 22xxx, 23xxx, 42501, PGRST1xx,
                 HTTP 400/409/413) — retrying the same input fails again
    server       5xx — retry later
    unknown
  `userMessage` always says plainly what happened and that nothing was saved. A request longer than 20 s is
  treated as offline.

7.4 Row mapping (data/remote/row_mappers.dart, text_limits.dart)
  Domain <-> table rows. Timestamps UTC ISO-8601; enums stored by Dart enum `name` (so appending enum values is
  safe; unknown values from a newer app map to a safe fallback); numerics rounded to the column's scale; text
  clipped and cleaned (NUL / unpaired surrogates removed) and numbers clamped so no value can violate a server
  CHECK constraint. `user_id` is added by the gateway; `updated_at` is owned by the server and never sent.


8. BACKEND: SUPABASE
--------------------
Project ref fyigpfuddgegvkibnvgd, URL https://fyigpfuddgegvkibnvgd.supabase.co (public; region Tokyo). Config is
injected at BUILD time with --dart-define-from-file=env/supabase.json (SUPABASE_URL + SUPABASE_ANON_KEY, i.e. the
PUBLISHABLE key only; env/supabase.json is git-ignored, env/supabase.example.json is the template). Without it the
app shows the "not configured" screen.

8.1 Tables (all: composite primary key (user_id, id) with a client-generated text id, user_id default auth.uid(),
    FK -> auth.users ON DELETE CASCADE, created_at, server-owned updated_at)
  profiles ................ one row per user (PK user_id), created by the on_auth_user_created trigger:
                            name, email (holds the username / private identifier), weight_kg, height_cm, age,
                            unit kg|lb, theme_mode dark|oled|system, default_sets, default_rep_min/max,
                            auto_rest_seconds, progression_enabled, weekly_session_target,
                            cardio_distance_unit_km, initialized_at. Clients can select/insert/update, NOT delete.
  exercises ............... CUSTOM exercises only: name, primary_muscle (7 broad groups), secondary_muscles[],
                            equipment, movement_pattern, instructions jsonb, tempo, muscle_targets jsonb
  workouts ................ routines: name, description, position (order), exercises jsonb (<=100), rest_seconds,
                            cardio_finisher jsonb
  rotations ............... PK user_id: workout_ids text[], current_index
  workout_sessions ........ history: workout_id (logical ref), name, workout_date, duration_seconds, exercises
                            jsonb (sets), cardio jsonb (finisher), notes
  cardio_sessions ......... kind (34 allowed values), workout_date, duration_seconds, distance_km, speed_kmh,
                            incline_pct, resistance, calories, avg_heart_rate, rpe, route_name, notes,
                            custom_activity_id (logical ref)
  cardio_goals ............ title, metric durationMinutes|distanceKm|sessions|calories, target, period week|month,
                            is_primary
  custom_cardio_activities  name, category, icon_key, fields[], round_seconds, rest_seconds, rounds
  Deliberately NO foreign keys for workout_sessions.workout_id, cardio_sessions.custom_activity_id and
  rotations.workout_ids[]: history must survive deleting a routine or a custom activity.
  Check constraints validate enums, ranges, text lengths and jsonb size (byte caps added in the hardening
  migration). No Storage buckets are used.

8.2 Functions (SECURITY INVOKER so RLS stays in force; auth.uid() inside; no user-id parameter; EXECUTE for
    `authenticated` only; search_path = '')
  sx_save_workouts(workouts jsonb, delete_ids text[], rotation jsonb)  upsert/delete routines + rotation atomically
  sx_finish_workout(session jsonb, rotation jsonb)   insert/update the session + set the rotation, idempotent on id
  sx_init_account(workouts, rotation)               one-time defaults; row-locks the profile so two devices
                                                    cannot both initialise; returns true only when it created them
  sx_reset_account_data()                           "delete all my data" (keeps account + profile, clears
                                                    initialized_at)
  delete_account()                                  SECURITY DEFINER; deletes only auth.uid()
  Triggers: sx_touch (server-authoritative updated_at; user_id and created_at immutable),
  handle_new_user (creates the profile).

8.3 Security model
  * Row Level Security enabled on all 8 tables; each has an owner-only policy `user_id = (select auth.uid())`
    (profiles split into select / insert / update — no delete). The `anon` role has no privileges.
  * Verified live on 2026-10-10 with an anonymous request using the publishable key: every table -> 401/42501,
    delete_account RPC as anon -> 42501.
  * TRUNCATE/REFERENCES/TRIGGER revoked from authenticated and anon (defence in depth).

9. DEVICE-LOCAL STORAGE (ISAR)
------------------------------
Isar (isar_community) now holds ONE singleton collection, AppMetaEntity (id = 1). It contains no user training
data and is never the source of truth for anything that exists on the server:
  * healthConnected ........ the user opted in to the platform health store (iOS cannot report read access)
  * workoutDraftJson ....... the in-progress workout (see 12.3)
  * ownerUserId ............ which account the draft belongs to
Account switching: when a different user loads, the previous user's draft is discarded.
Logout / expired session / account deletion: draft + owner are removed. The health opt-in is kept.
(Older builds also stored a maximum-workout-length preference and an auto-end notice; those fields were removed.) Old builds stored every table in Isar; those collections are no longer in the schema, so Isar
drops them when it opens an old file (local-only data of the pre-online builds was NOT migrated — the app was
unreleased).
Other device files: health_sync.json (Health Connect queue, receipts, imported-record ids, heart-rate stats; written
atomically via temp + rename; local only, never uploaded) and the Supabase SDK's own session storage.
Android Auto Backup / device transfer is OFF (allowBackup=false).
Regenerate Isar code after editing entities.dart: `dart run build_runner build`.

12. STRENGTH LOGGING & PROGRESSION
----------------------------------
12.1 Active workout page (features/active_workout)
  * Layout: strength-only, or a mixed layout (strength + cardio block) when the routine has/gains a cardio block.
  * Exercises are grouped into muscle sections with sub-area captions (WorkoutSections.groupContiguous: a running
    workout is never reordered); headers show exercises done/total and sets done/total; finished sections dim.
  * Per set: weight, reps, done toggle (the live strength logger has no RPE input; RPE is kept for cardio sessions and
    stays readable/editable in history, imports and exports — product decision 2026-10-11: keep RPE); numeric keypad sheet; +/- stepper (2.5 kg / 5 lb steps); "same as
    last set"; remove set with undo; add set. A weighted exercise cannot be marked done at 0 kg (the keypad
    opens). PREV column shows the previous session's sets.
  * Progression suggestion chip ("Use ...") applies the recommended weight/reps to the not-yet-done sets.
  * No rest timer, no elapsed timer, no automatic ending (removed). Plate calculator sheet, notes, per-session exercise swap (Smart Swap), add exercise (inserted at its canonical place
    in the muscle section), haptic feedback on completing a set / finishing, screen kept awake.
  * Finish: builds the session (only done sets; exercises with none are dropped; workoutDate = backdate ?? start;
    createdAt = now) and saves it with sx_finish_workout (session + rotation move in ONE call). If the server
    call fails, the draft is kept and the screen offers Retry. Discard asks first; leaving with nothing logged
    exits silently. A Retry path exists for "session saved but rotation did not move".
  * Backdating: a workout can be logged for a past date (from the calendar); the rotation is NOT advanced.
  * Workout complete page: summary (duration, volume, sets), PR cards with a staggered pop (<= 450 ms, one
    haptic), comparison with the previous session per exercise, heart-rate card (opt-in), cardio block summary,
    "Next up: <workout>".
12.2 Progression (ProgressionService — conservative double progression)
  * Needs >= 2 done sets in the last session and >= 2 sessions of history, load-tracked exercise (not
    bodyweight/band/timed work such as planks, holds, carries) and positive weight; otherwise only the last
    performance is shown.
  * "Working weight" = the heaviest weight with 2+ sets or that reached the rep minimum; otherwise the most
    common weight (a lone heavy single never dictates).
  * If every set at that weight hit the top of the rep range (and there were >= 2 such sets) -> increase the
    weight by the exercise's increment; otherwise keep the weight and ask for last best reps + 1 (capped at the
    top of the range). If the last session is older than 21 days -> "start again from <weight>".
  * Increments (display units): barbell compounds 5 kg, machines/cables/dumbbell compounds 2.5, small dumbbell
    isolation 1, other small isolation 2.5, kettlebells 2; lb: 5 or 2.5. Can be turned off in Profile.
12.3 Draft persistence
  Every change in the running workout is saved (debounced) as a WorkoutDraft JSON in Isar so an OS kill or crash
  loses nothing. "Resume workout" appears on Today. The draft belongs to the signed-in account and is wiped on
  logout / account change. A conflicting older draft is resolved before persistence continues.
12.4 No automatic ending
  A workout stays open until the user finishes or discards it. There is no maximum length, no heads-up and no
  automatic save. A draft left from a previous run is offered on Today as "Resume workout".


13. MUSCLE TAXONOMY, PROFILES, RECOMMENDER
------------------------------------------
Pure Dart in lib/domain. Practical gym terminology, not an anatomy claim.
  Regions (12): Chest, Back, Shoulders, Biceps, Triceps, Forearms, Quadriceps, Hamstrings, Glutes, Adductors,
  Calves, Core. Each maps to the 7-way storage MuscleGroup (forearms -> biceps; quads/hams/glutes/adductors/calves
  -> legs), which never changes, so the detailed layer needed no schema change for built-ins.
  Sub-muscles: Chest (upper/mid/lower), Back (lats, upper back, traps, lower back), Shoulders (front/side/rear
  delts), Biceps (long head, short head, brachialis), Triceps (long/lateral/medial), Forearms (wrist flexors,
  wrist extensors, brachioradialis/grip), Quads (rectus femoris, vastus lateralis/medialis/intermedius),
  Hamstrings (biceps femoris, semitendinosus, semimembranosus), Glutes (max/med/min), Adductors (inner thigh —
  own region so hip adduction never credits the glutes), Calves (gastrocnemius, soleus, tibialis = front of the
  lower leg), Core (abs, obliques, deep core).
  SectionMuscle (8): Chest, Back, Shoulders, Biceps, Triceps, Forearms, Legs, Core — the muscles that own a workout
  SECTION in preview/editor/logger.
  Profiles: every one of the 420 built-in exercises has structured MuscleTargets (primary / assisting, a sub-muscle
  only where defensible, else the whole region — "no fake precision"). Example: Lat Pulldown = Back > Lats
  (assisting biceps, upper back); Incline DB Press = Chest > Upper chest (assisting triceps, front delts);
  Romanian Deadlift = hamstrings (assisting glutes, lower back). Profiles are written in a small DSL
  (profile_dsl.dart, profiles/ per region). Custom exercises use the same structure (stored as muscle_targets).
  Weights: primary set = 1.0, assisting = 0.5 (one place: MuscleWeights). "Direct" coverage counts only primary
  work (bench press = direct chest work, only assisting for triceps/front delts).
  Coverage (MuscleCoverage): for a workout, a program (rotation per week) or logged history: direct vs weighted
  sets; levels none/low/moderate/high judged per week on WEIGHTED sets — region thresholds 4 / 10, sub-muscle 2 / 5,
  adductors 2 / 6 (practical guidelines for a UI hint, not scientific claims).
  Recommender (ExerciseRecommender): ONE engine for day generation, replacement ranking and informational "might
  be under-trained" hints. Deterministic (ties -> catalog order). A day stops adding exercises to a muscle once
  its per-day target is covered; the target depends on weekly adequate sets divided by how often the region is
  trained (from days/week). Hints are optional suggestions, never commands. SmartSwapService delegates to it.
  Equipment: onboarding asks which equipment the user has (step after the split choice; "Full gym" / "Bodyweight
  only" shortcuts; saved in profiles.equipment and editable in Profile). Presets are fitted with ProgramEquipmentFit;
  the custom path's suggestions (SetupCatalog.suggestSection) and the recommender use allowedEquipment. Manually
  picked exercises are never restricted. Changing the preference later never rewrites a saved program.
  Pattern repetition: ExerciseRecommender.forDay takes patternRepeatPenalty (1.5) off a candidate for every
  exercise of the same movement pattern already in the day (measured: removed the double calf-raise / third curl).
  Difficulty (2026-10-12): Exercise.difficulty (null = unspecified/custom). Experience level (profile, default
  intermediate, asked in onboarding after equipment, editable in Profile) drives AUTOMATIC suggestions only:
  beginner = hard filter (no advanced) with a controlled fallback (ONE advanced exercise for a region that would
  otherwise get no direct work; reported and listed on Review); intermediate = advanced allowed but penalised
  (-2.5, never below "useful", so coverage is kept); advanced = everything. Presets are fitted the same way
  (ProgramEquipmentFit.fitReport: beginners swap advanced curated exercises, intermediates avoid advanced
  REPLACEMENTS). Manual picks, the swap sheet and custom exercises are never restricted. Changing the level or
  adding catalogue metadata never touches a saved program (a saved workout stores only id/sets/reps).
  WorkoutSections: canonical arrangement — one section per muscle; MAIN exercises (general/compound) first with no
  sub-header, then sub-areas in canonical order (Back: Lats + Upper back main, then Traps, then Lower back; custom
  exercises count as main). Section headers show only when a workout has 2+ sections.


14. SCHEDULE SETUP (ONBOARDING)
-------------------------------
Flow (features/onboarding): choose a program -> [custom days] -> [one page per day unless Quick start] -> "How
many days a week?" (1-7) -> Review -> Save. Entry points: right after registering, Workouts tab, Profile ("Set
up my schedule"), and the dismissible Today prompt. Skippable everywhere; leaving midway asks before discarding.
  * Presets: Full Body (A/B/C), Upper / Lower, Push / Pull / Legs, Bro split (Chest, Back, Shoulders, Arms, Legs),
    or Custom.
  * Quick start takes a preset as is. Customize lets the user tick exercises per day and per muscle, grouped into
    practical sub-sections (e.g. Back -> Lats . Pull-ups / Pulldowns, Upper back . rows, Traps, Lower back; no
    section holds more than 13 exercises; big sub-areas are split into "families" such as Mid chest . Presses +
    Cable, push-ups & band), with a one-line reason per suggestion (classic compound first) and sets/reps steppers.
    "+ Add exercise" creates a custom exercise and ticks it immediately.
  * Custom: name your days, choose muscles per day (reorder/add/remove); suggestions come from the recommender.
  * Days per week only sets the weekly session goal; the program stays a SEQUENCE.
  * Review: sets and minutes per day, a collapsible "Muscle coverage" summary and calm optional hints.
  * Save = ScheduleBuilder + WorkoutRepository.saveSchedule -> ONE atomic sx_save_workouts call: new routines +
    new rotation; previous routines that are not reused are archived (kept), archived ones can be restored. When
    routines already exist, a confirmation first explains that the rotation will be replaced.
  New accounts get NO routines (SeedData.defaultWorkouts is test data only, used by the in-memory MemoryStore).
  The 420-exercise catalogue splits per region: back 74, hamstrings/glutes 55, quads 52, biceps/forearms 50,
  core 43, shoulders 43, chest 42, triceps 32, calves/adductors 25, other 4.

16. HEALTH INTEGRATION (HEALTH CONNECT / APPLE HEALTH)
------------------------------------------------------
Everything is opt-in and OFF by default; the app explains what it will read/write BEFORE the system permission
sheet. Samsung Health works through Health Connect (StationX never talks to Samsung directly, no Samsung SDK).
Android permissions requested per feature (declared in AndroidManifest.xml; INTERNET is also declared):
WRITE_EXERCISE, WRITE_DISTANCE, WRITE_TOTAL_CALORIES_BURNED | READ_EXERCISE,
READ_DISTANCE, READ_TOTAL_CALORIES_BURNED, READ_ACTIVE_CALORIES_BURNED, READ_HEART_RATE, READ_STEPS (needed only
because the plugin's workout reader sums steps per session; steps are neither stored nor shown) |
READ_HEALTH_DATA_HISTORY (optional older data). The permissions-rationale activity and the Android 14
VIEW_PERMISSION_USAGE alias are declared.
  Features
  1. (removed) The recovery summary (sleep / resting heart rate) no longer exists; the base "connect" permission
     now only reads exercise sessions.
  2. Save workouts (write, HealthFeature.writeWorkouts): each finished cardio/strength session becomes ONE exercise
     session (type, title, start/duration, ONLY the distance/calories the user logged — no heart rate, sets, reps
     or weights). Edits replace StationX's own record, deletes remove it; StationX only ever deletes records it
     created (receipts remembered). Failed writes are queued on the device and retried; they never block logging.
  3. Fill in heart rate and calories (read, HealthFeature.enrichCardio): suggests average HR / calories for a
     cardio session's time window; applied only after the user confirms. Also average/max HR on a finished workout
     (kept locally in health_sync.json), a recent-HR chip while training (polls every 15 s, hides when no sample in
     the last 2 min — Health Connect is not a live stream) and an average HR trend (7/14/30 days, read on
     demand, not stored).
  4. Import workouts (read, HealthFeature.importWorkouts): lists sessions other apps/watches recorded (last 30 days
     by default, up to 90 per preview; all history with the extra permission, read in 60-day windows), preview first;
     cardio -> cardio sessions, watch strength sessions -> strength sessions with duration/calories only (marked
     "Imported from Health Connect"). Never duplicated. Optional AUTOMATIC import when the app opens (throttled,
     silent on failure). Own StationX records are excluded.
  5. "Connect your watch" page: a read-only 7-day check that finds the first step that is not working (store
     missing -> permissions -> no recent data -> ok).
  The sync service observes the session/cardio repositories so every new or edited session anywhere is mirrored
  without feature code calling it; sessions that merely arrive from a load or an import are not written back.
  Health data that is read stays on the device unless the user accepts/imports it into their history (then it is
  ordinary workout data stored in the account). iOS (Apple Health / HealthKit) is coded and wired but NEVER built.


17. IMPORT / EXPORT
-------------------
  Import from Gym Tracker (Profile > Integrations): a one-time migration from the author's older app.
  The older app's Settings > Data > "Export Data" writes a versioned JSON ("gym_tracker_export" v1; spec in
  gym_tracker/docs/EXPORT_FORMAT.md). In StationX: choose the file (or paste, up to 10 MB in the UI; files over 50 MB
  are refused) -> preview -> Import.
    * Only completed workouts; workoutDate = when the workout was started; createdAt = now.
    * Importing the same file twice adds nothing (ids are gt_s<id>).
    * Existing data is never modified or deleted. Exercises matched by exact name, then a curated alias list, then
      a previously imported custom exercise, else a new custom exercise with inferred muscle group/equipment.
    * PRs / e1RM are recomputed from history; achievements ignored. Optional: make the next workout match where
      Gym Tracker left off. Weights are kg on both sides. Malformed entries are skipped one by one.
    * Applying uses SessionRepository.addAll -> upserts to the server in batches of <= 100.
    * Code: lib/data/import/, lib/features/profile/gym_tracker_import_flow.dart.
  Export (Profile > Export your data): plain-text JSON or CSV of profile, sessions and cardio built by
  ExportBuilder (formatting only, no calculations); "Save as file" (system save dialog) or "Copy to clipboard".

19. SECURITY & PRIVACY
----------------------
  * No analytics, ads, tracking or third-party crash-reporting SDKs. The only network peer is Supabase.
  * The app needs the INTERNET permission (login, loading and saving are online).
  * Passwords go to Supabase Auth only; never stored/logged by the app; the server keeps a one-way hash. No e-mail
    or phone is collected; the username maps to a private "<username>@stationx.local" identifier.
  * Server: RLS owner-only on every table, anon denied, check constraints and size caps, SECURITY INVOKER
    functions with auth.uid(), account deletion via a SECURITY DEFINER function limited to the caller.
  * Client: only the publishable key can ever be in the app (the config guard refuses secret keys / sbp_ tokens /
    service_role JWTs); secrets are never committed (env/supabase.json, key.properties, *.jks are git-ignored);

24. GLOSSARY
------------
  Rotation ........ the ordered list of workouts you cycle through; an index points at the current one
  Routine / Workout  one training day (e.g. "Back + Triceps") with exercises, sets and rep ranges
  Archived ........ routines no longer in the rotation but still kept
  Session ......... one completed strength workout in history (WorkoutSession); cardio has CardioSession
  Draft ........... the saved snapshot of the workout in progress (device only)
  e1RM / 1RM ...... estimated one-rep max (Epley)
  PR .............. personal record
  RPE ............. rate of perceived exertion (0-10)
  RLS ............. Row Level Security (PostgreSQL) — makes every row owner-only
  RPC ............. a Postgres function called through the Supabase API (the sx_* functions)
  Read model ...... the in-memory copy of the signed-in user's data the screens read from
  Epoch ........... counter that invalidates in-flight loads/writes when the user changes
  Publishable key . the public Supabase client key (safe in the app, protected by RLS)
  Health Connect .. Android's health data store (Samsung Health and most watches sync into it)
